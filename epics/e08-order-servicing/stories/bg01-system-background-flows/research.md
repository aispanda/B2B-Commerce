# BG01 official research and planned tests

Read on 12 November 2026. This public document contains reusable platform research, not client configuration or installation evidence. Official Help article text was inspected; navigation/CSS error shells alone were not evidence. All transactional tests below are **NOT RUN**. Return to the [story](README.md).

## Core capability contracts

| Flow / capability | Documented trigger or contract | Dependencies and effects to verify in the target environment |
|---|---|---|
| Create Order Summary | The OM catalog describes an Order create/update whose StatusCode is Activated. Create Order Summary takes original order ID and returns summary ID. | Delivery group and related records, managed/unmanaged lifecycle, required fields, duplicate prevention, high-scale and checkout coexistence. |
| Create Process Exception | The official event reference says ProcessExceptionEvent triggers the default flow. | Actual subscriber, recognized event types, correlation/category, effective identity, exception-record visibility, unsupported types and replay. Other flows can emit the event; that differs from invoking a subflow. |
| Create Tax Transaction | Release documentation describes tax recording after summary creation. | Exact event/action signature, store provider, merchant/test mode, original tax-transaction key and Order Events configuration. Tax calculation is distinct from transaction reporting. |
| Record Tax Reversals | Documented return/cancellation tax reversal in an external system. | Exact subscriber, original transaction, partial/full amount, currency, duplicate and out-of-order handling. Tax reversal alone does not establish cash refund. |
| RMA Create Credit Memo and Ensure Refunds | The catalog describes managed Return Order updates with StatusCategory Closed. | Inspect actual status predicate and schedule, received/rejected quantities, change orders, credit, fee invoices, payment-credit/refund branches and fault behavior. Do not assume a copied flow exactly matches current catalog wording. |
| Ensure Refunds for Excess Funds | Ensure Refunds Async supports refunding excess funds through a provider. | Inspect the actual flow's event/caller and filters, amount source, outstanding work, duplicate/concurrent changes and correlation. A template name does not establish its trigger. |

## Checkout and related automation

Preserve `CheckoutFlow` as its actual metadata type where reported. A buyer can start the parent checkout while it invokes subflows; some invoked steps can still contain buyer interaction. “Subflow” alone does not mean an ordinary Autolaunched flow or a safe standalone endpoint.

Reconcile the supplied inventory individually for Activate Order, Cart To Order, Checkout Session, Checkout Summary, Confirm Price, Delivery Method, Error, Inventory, Order Confirmation, Payment and Billing Address, Shipping Address, Shipping Cost, Taxes and Update Checkout State. Inspect exact internal actions and actual callers privately. Potential effects include inventory operations, external tax/shipping calls, payment authorization/capture, order activation and downstream summary creation; do not assume every subflow performs each effect.

The supplied [legacy checkout-flow reference](https://developer.salesforce.com/docs/commerce/salesforce-commerce/guide/b2b-b2c-comm-setup-checkout-flow.html) timed out during this research, leaving template-specific action mapping unverified. [How Standard B2B Commerce Checkout Works](https://developer.salesforce.com/docs/commerce/salesforce-commerce/guide/b2b-comm-checkout-how-standard-works.html) and [Customize a Checkout Component for LWR](https://developer.salesforce.com/docs/commerce/salesforce-commerce/guide/b2b-b2c-comm-create-checkout-component.html), developer guides, describe current API/calculator and component architecture. They do not establish which legacy templates a store uses. The LWR guide requires sequential cart/checkout mutations.

External-channel exception and B2C concierge templates require explicit applicability and caller decisions. Do not treat adjacent product templates as B2B order-lifecycle functionality solely because they are Autolaunched. Distributed Order Management is an additional license/package-dependent research candidate from the official catalog, not an installed capability inferred from a name search.

## Test strategy — proposed, NOT RUN

Before execution, identify one accountable owner and executor, exact environment, reserved synthetic fixtures, provider test accounts, callback/egress boundaries, safe notification routing, effective permissions and approved business treatment. An edition or sandbox label alone does not establish financial isolation. Review subscriptions and other automation; queued jobs, events and provider effects must not be assumed contained by Flow debug rollback.

| Suite | Cases | Expected evidence / failure check | ACs |
|---|---|---|---|
| Summary | Activated/nonactivated order; missing related data; replay; high-scale versus ordinary channels; lifecycle | One correct summary graph or explicit expected failure; no competing producer | 02 |
| Exception | Supported and unknown type, missing correlation, duplicate, insufficient access | Correct visible exception or explicit unsupported handling; no sensitive error leakage; inspect default/fault routes | 03,08 |
| Tax | Nonzero/zero tax, partial return, cancellation, replay/out-of-order, provider timeout/failure | Correlated transaction/reversal and amount/currency agreement; no cash-refund assumption | 04,08 |
| RMA | Full/partial/rejected receipt; zero-value, delivery and fee lines; unmanaged; alternate status; repeat close; invoice missing | Correct processed/split quantities, change order, credit/fee invoice and approved payment-credit/refund; partial effects reconciled | 05,08 |
| Excess funds | Cancellation/non-cancellation; zero/negative/positive/null; replay; overlapping changes while refund pending | No unintended refund; actual total refunded stays within eligible owed balance; stale cumulative amounts handled | 06,08 |
| Settlement | Unpaid invoice, captured test payment, insufficient refundable balance, multiple methods, fee offset, delayed/failed callback | Credit balance and provider refund separately reconciled; job status never sufficient; bounded recovery | 05,06,08 |
| Integration/access | Checkout architecture; bot/channel applicability; service role and wrong-account/unauthorized role | Include/defer/exclude decisions, valid caller/context, denied unauthorized effects and operations investigation access | 07,08 |

Agree expected quantities/amounts before each test and capture private before/after and asynchronous/provider evidence. Stop on unexpected effects. Inspect durable records, provider state and outstanding work before retry; do not delete financial history or reset balances to make tests pass. Permit at most one controlled replay after reconciliation, with a finite polling timeout and a named recovery owner. Arrange fresh independent review of changes/evidence before implementation handoff or release.
