## Scope and evidence

The baseline covers [O05 eligibility](stories/o05-consignment-eligibility/README.md) and [O06 fill-up checkout](stories/o06-consignment-fill-up/README.md). An eligible buyer may request an initial fill-up or later manual replenishment through the same checkout. SAP and fulfillment own stock and stock movements, replenishment rules and thresholds, fulfillment, consumption reporting and pricing, invoicing and payment. Salesforce captures the buyer's manual request. The MVP also shows fulfillment and shipment updates returned by SAP and gives eligible buyers read-only visibility into SAP-reported consumption. The field mapping, synchronization and access rules remain pending. Authorized invoice-document access is separate under [O10](https://github.com/aispanda/B2B-Commerce/blob/main/epics/e04-post-order/stories/o10-invoice-access/README.md). The confirmation and failure contract belongs to [E03, O07 and O08](https://github.com/aispanda/B2B-Commerce/tree/main/epics/e03-order-submission). The consumption-billing PO rule remains an SAP business question independent of the optional fill-up PO.

## Proposed design for review

1. **Eligibility and account context.** Keep the selected customer and authorized catalog bound to the cart. Use the SAP-sourced account decision to offer regular and consignment checkout. The preferred starting design is an account-level value synchronized to Salesforce, with a defined freshness and revocation rule. If SAP requires live eligibility, use a submit-time SAP validation and define the behavior for an unavailable decision. Reauthorize the buyer and validate account eligibility on the server at entry and before dispatch. A stale, missing or ineligible decision blocks consignment under the proposed design. Re-evaluate after account switch and clear stale consignment intent. Persist one order type through checkout and submission.
2. **Fill-up review.** Reuse the selected account's catalog, cart, quantities and one authorized ship-to with a shipping method. Keep an optional PO field for this order type and send a supplied PO according to the SAP contract. Show SAP-returned reference prices separately from **Amount due now: $0** with the consumption-billing note. Use a no-charge path whose server-side behavior is verified in the target checkout. Confirm any tax and shipping display against the approved zero-due presentation and verify that the fill-up triggers no payment authorization or capture. The same path accepts manual replenishment requests.
3. **Submit and reconcile under O07/O08.** Reuse one server-side submission path where possible. Map the customer and authorized ship-to, SKU/quantity, shipping method, optional PO, SAP consignment order type, and a stable submission reference to the external contract. Persist and reuse the same attempt reference for the same submission, including concurrent requests and recovery after timeout. The proposed contract needs a supported lookup or deduplication behavior on the SAP side. SAP acceptance supplies the SAP order reference and any applicable line-level contract or tender references. Correlate returned lines with the submitted lines and expose confirmation only after SAP acceptance and the supported Salesforce order state are reconciled. A Salesforce reference on its own cannot establish SAP acceptance.
4. **Failure handling under O08.** Distinguish explicit rejection from an unresolved timeout or connection failure. Give the buyer the existing Customer Care route and a support reference. If a Salesforce record already exists, preserve its failed or unresolved state. Customer Care checks SAP before a replacement order is placed. If SAP accepts and Salesforce finalization fails, reconcile the existing acceptance against the same reference before any further submit. Use sanitized technical evidence that correlates the attempt, SAP response and storefront outcome.

The storefront route and SAP ordering contract determine whether orchestration can obtain acceptance before Salesforce finalizes or must retain a local pending record first. Salesforce documents a staged Place Order Actions API for stores with Streamlined Place Order enabled. Its validation extension is cart-scoped, permits one callout and disallows DML and asynchronous work. Validate the store's configured path and the supported no-payment route before selecting a hook. Keep durable submission state and SAP recovery outside a validation hook that cannot persist them. [Place Order Actions API](https://developer.salesforce.com/docs/commerce/salesforce-commerce/guide/b2b-comm-checkout-place-order-action-api.html) · [CheckoutPlaceOrder extension constraints](https://developer.salesforce.com/docs/commerce/salesforce-commerce/references/comm-apex-reference/CheckoutPlaceOrder.html)
